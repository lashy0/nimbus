## Генерация

Файлы в `firmware/assets/` создаются официальными конвертерами LVGL из `artwork/`;
вручную их не правят. Сгенерированные файлы хранятся в Git, прошивка конвертеры
не запускает. Сам генератор (локальный `tools/`) в Git не входит, поэтому ниже
записано всё, что нужно для воспроизведения результата.

Проверенные версии:

- `lv_font_conv` 1.5.3 — шрифты;
- `lv_img_conv` 0.4.0 — изображения, тот же код, что у онлайн-конвертера LVGL 8.
  Он написан на TypeScript и запускается через `ts-node -s lv_img_conv.js`; нужны
  `typescript` 4.9.5 и `@swc/core` 1.16.18.
- `canvas` 3.2.3 через npm `overrides`: у версии 2.11.2 из зависимостей
  `lv_img_conv` нет готовой сборки для Node.js 24, а сборка из исходников
  на Windows требует MSVC и GTK.

Повторная генерация с этими версиями даёт побайтно одинаковый результат.
Перед пересозданием `firmware/assets/fonts` и `firmware/assets/img` проверяется наличие всех исходников,
включая локальные OTF, чтобы не удалить готовые файлы при их отсутствии.

### Имена

Каждый файл `artwork/img/<group>/<name>.{jpg,png}` даёт
`firmware/assets/img/<group>/<name>.bin`, где `-` заменён на `_`; у батарей дополнительно
убран префикс `battery-`. Пример: `batt/battery-1-not-charging.jpg` →
`batt/1_not_charging.bin`, `face/temp-minus-closed-eyes.jpg` →
`face/temp_minus_closed_eyes.bin`.

### Изображения

```text
lv_img_conv <artwork> --force --color-format CF_TRUE_COLOR --output-format bin
            --binary-format ARGB8565_RBSWAP --output-file <assets>
```

- Без дизеринга.
- Формат LVGL 8.4: 4-байтовый `lv_img_header_t`, `LV_IMG_CF_TRUE_COLOR` (`cf=4`),
  RGB565 без альфа-канала, 2 байта на пиксель.
- Порядок байтов big-endian, как при `LV_COLOR_16_SWAP=1`: так ST7789 принимает
  данные по SPI. Конфигурация LVGL в `ui` должна с этим совпадать. Флаг
  `--swap-endian` конвертера влияет только на вывод в C, для `bin` порядок задаёт
  `ARGB8565_RBSWAP`.
- Альфа-канал PNG батарей отбрасывается. Во всех четырёх текущих PNG каждый пиксель
  непрозрачен (alpha=255), поэтому изображение не меняется. Для новых PNG
  с прозрачностью нужно решить отдельно: `CF_TRUE_COLOR_ALPHA` или фон в оригинале.

### Шрифты

```text
lv_font_conv --font <otf> --size <px> --bpp 4 --no-compress --no-kerning
             --format bin -r <ranges> -o <fnt>
```

Формат `bin` загружается `lv_font_load`.

| Файл | Начертание, размер | Набор |
| --- | --- | --- |
| `sf_b_10.fnt` | Bold, 10 px | battery |
| `sf_sb_15.fnt`, `sf_sb_30.fnt` | Semibold, 15 и 30 px | text |
| `sf_sb_50.fnt`, `sf_sb_60.fnt` | Semibold, 50 и 60 px | digits |

- digits: `0x20,0x25,0x2B,0x2D-0x2E,0x30-0x39,0xB0` — пробел, `%`, `+`, `-`, `.`,
  цифры, `°`.
- battery: digits и `0x42,0x53,0x55` — буквы `B`, `S`, `U` для надписи `USB`
  у батареи (добавлено в v2; остальные шрифты совпадают с v1).
- text: `0x20-0x7E,0xA0-0xAC,0xAE-0xFF,0x400-0x45F,0x2116` — ASCII, Latin-1 без
  мягкого переноса `U+00AD`, кириллица, `№`.

Размеры и наборы восстановлены из шрифтов v1 и дают побайтно те же `.fnt`.
При разработке экранов их можно менять; изменение записывается в эту таблицу.

можно достоверно определить.

`firmware/main/CMakeLists.txt` собирает из `firmware/assets/` образ SPIFFS (`spiffs_create_partition_image`)
для раздела `storage`; `idf.py flash` записывает его вместе с прошивкой. `composition`
монтирует раздел в `/spiffs` без форматирования при ошибке. LVGL читает файлы через
драйвер STDIO с буквой `S`: `S:/spiffs/fonts/...` и `S:/spiffs/img/...`. Имена до
64 символов (`CONFIG_SPIFFS_OBJ_NAME_LEN=64`). В `firmware/assets/` не добавляются документы,
исходники и артефакты сборки прошивки.

## Хранение и бюджет памяти

Принятый базовый вариант — SPIFFS и загрузка `.fnt` во время запуска.
EMBED_FILES для изображений и LittleFS остаются альтернативами для измерения
на этапе 2; решение о смене хранения пока не принято.

Пять шрифтов суммарно занимают 80840 байт файлов (80752 до добавления `USB`
в `sf_b_10.fnt`). `lv_font_load` в LVGL8
загружает данные в heap; размер файлов не равен гарантированному расходу кучи.
После каждого шрифта и создания draw buffers/экранов фиксируются свободная
память, minimum free и largest block, отдельно для DMA-capable памяти.

Измерено 19 октября 2026 (тестовый экран, портрет 135×240, данные из лога `ui`):

| Этап | Расход internal heap | Время загрузки |
| --- | --- | --- |
| LVGL port + 2 draw buffers по 20 строк | 22,5 КиБ | — |
| `sf_b_10.fnt` | 0,7 КиБ | ~10 мс |
| `sf_sb_15.fnt` | 15,4 КиБ | ~70 мс |
| `sf_sb_30.fnt` | 50,4 КиБ | ~410 мс |
| `sf_sb_50.fnt` | 6,5 КиБ | ~30 мс |
| `sf_sb_60.fnt` | 9,3 КиБ | ~40 мс |

Все пять шрифтов — 82,3 КиБ heap. После построения экрана свободно 235920 байт
internal, minimum 231652, наибольший блок 110592; DMA-capable свободно 177600.
Без кэша чтения (`CONFIG_LV_FS_STDIO_CACHE_SIZE=0`, как в v1) `sf_sb_30.fnt`
загружался ~4,6 с, и запуск UI превышал лимит 5 с. Кэш 4096 байт выделяется на время
открытия файла и сократил запуск UI до ~0,7 с. Многократная навигация и утечки
ещё не проверялись.

При пробе EMBED_FILES проверяются реальный LVGL8 bin header, выравнивание,
формат цвета и чтение из flash. SPI DMA по-прежнему может требовать внутренний
буфер; обещание «нет расхода RAM» к полному конвейеру отрисовки неприменимо.
LittleFS подключается явной закреплённой зависимостью и с собственной упаковкой;
сравниваются mount, первое/повторное рисование, RAM и поведение при ошибке ресурса.
