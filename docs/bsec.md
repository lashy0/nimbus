# Контракт BME680 / BSEC2

Это спецификация этапов 3 и 5. Библиотека BSEC пока не подключена к новой основе.
Владельцем enum фазы, output quality и всего экземпляра BSEC является `sensing`.

## Фазы и валидность

Правила применяются по порядку. `stabilization` и `run_in` считаются завершёнными
только после получения соответствующих outputs со значением >= 0,5.
Не полученное значение не приравнивается к true.

| Условие | Фаза | Отображение static IAQ |
| --- | --- | --- |
| Инициализация BME680/BSEC не завершена | INITIALIZING | Ожидание датчика |
| Сервис в состоянии ошибки/retry | ERROR | `--`, ошибка; историческое значение только с отметкой stale |
| BSEC запущен, но нет outputs, нет stabilization/run_in либо accuracy=0 | WARMUP | Число и оценка воздуха скрыты, показан прогрев |
| stabilization=1, run_in=1, accuracy=1 | CALIBRATING | Число с пометкой калибровки / низкой достоверности |
| stabilization=1, run_in=1, accuracy=2 или 3 | READY | Число; accuracy=2 — средняя, 3 — высокая достоверность |

Для первого варианта качество берётся из `BSEC_OUTPUT_IAQ.accuracy`; static IAQ
должен реально присутствовать в output. Отдельные accuracy всех outputs сохраняются
для диагностики. Поведение static IAQ accuracy сверяется при интеграции SDK,
а не предполагается равным полю IAQ без проверки.

`display_iaq_valid` требует свежий static output, завершённые stabilization/run_in,
accuracy>=1 и отсутствие ошибки текущего результата. Фаза READY не означает
высокую accuracy=3 и не отменяет независимый признак stale. При падении качества
фаза может вернуться назад. T/RH имеют отдельные timestamp/validity.

Пример из v1 `acc=0, stab=yes, run_in=no` однозначно относится к WARMUP.
Отсутствие новой порции BSEC outputs не обновляет timestamp показания.

## Конфигурация

Целевая версия BSEC — 2.6.1.0. Проверенный набор конфигураций этой версии содержит:

| Профиль | Blob | Подписка |
| --- | --- | --- |
| Базовый LP | `bme680_iaq_33v_3s_4d/bsec_iaq.config` | `BSEC_SAMPLE_RATE_LP` |
| Будущий ULP | `bme680_iaq_33v_300s_4d/bsec_iaq.config` | `BSEC_SAMPLE_RATE_ULP` |

Префикс пути в официальном пакете — `src/config/bme680/`. Выбор 33v соответствует
питанию датчика 3,3 В; 4d остаётся фиксированным проектным профилем. На 28d
автоматически не переходим и не трактуем суффикс как время обязательного прогрева.
При подключении фиксируются SHA-256 библиотеки и обоих реально используемых blobs.
Контейнер `.config` разбирается по формату пакета: наличие префикса длины проверяется,
а не отбрасывается безусловно.

В `bsec_datatypes.h` версии 2.6.1.0 есть
`BSEC_W_SU_SAMPLERATEMISMATCH = 14`: частота подписки может не совпадать с config.
Поэтому менять только delay или только subscription с LP blob недостаточно.
Предупреждение 14 считается неуспешной сменой профиля; произвольные положительные
коды BSEC нельзя все без разбора объявлять успешным измерением.

До этапа 5 доступен только LP. Запрос ULP возвращает unsupported и не меняет
effective profile. Перед включением LP↔ULP необходимо:

1. Проверить инструкции точного пакета 2.6.1.0 о смене config и переносе state.
2. На sensing task завершить текущий measurement и применить подходящий blob /
   подписки; проверить все return codes и `next_call`.
3. Загрузить state только при доказанной совместимости. Пока она не подтверждена,
   state хранится отдельно по profile + config hash + library version.
4. Если нужен reset/reinit алгоритма, явно опубликовать WARMUP; не маскировать
   потерю калибровки под непрерывный READY.
5. Проверить LP→ULP→LP на плате: timestamps, качество, отсутствие mismatch,
   восстановление после reboot. Только затем разрешить профиль пользователю.

Доступные headers подтверждают наличие разных blobs и диагностику mismatch,
но не доказывают бесшовную совместимость state между ними. Этот вопрос остаётся
открытым до проверки integration guide / опыта на точной версии.

## Сохранение состояния

Все вызовы get/set state выполняются sensing task. Запись storage содержит версию
формата, версию BSEC, profile, config hash, длину, checksum и качество на момент
сохранения. Чтение проверяет поля до передачи blob библиотеке.

Проектная политика:

- Первый checkpoint после первого готового результата с accuracy>=1 и обоими
  признаками stabilization/run_in; повтор одного этапа не вызывает запись.
- Отдельно сохранить первое достижение accuracy=3.
- Далее checkpoint каждые 6 часов при наличии нового пригодного результата.
- При штатной остановке сохранить изменившееся доступное state в пределах
  общего таймаута остановки. Незавершённая калибровка может сохраняться как
  checkpoint с соответствующим качеством, но не как доказательство READY.
- Между автоматическими записями минимум 60 с; сохранение при штатном выключении
  может обойти это ограничение. Если state не изменилось, повторная запись не нужна.
- Ошибка сохранения не обновляет отметки last_saved и не стирает прежний blob.
  Реинициализация после ошибки не сохраняет сомнительный state поверх хорошего.

Интервал 6 часов соответствует примеру сохранения Bosch; checkpoint на этапе
калибровки и минимальная пауза — политика Nimbus, а не обещание производителя.
Восстановленное state не превращается в свежие показания до реальных outputs.

## Подключение и лицензия

В официальном `LICENSE.md` BSD-3-Clause относится к Arduino wrapper и примерам.
Бинарная библиотека, `src/inc` и `src/config` покрываются отдельными условиями
Bosch. Разрешение BSD нельзя распространять на `libalgobsec.a` по аналогии.

Ссылка официального репозитория на полный текст условий при этой проверке
вернула 404. Право публичного распространения standalone `.a` и config blobs
поэтому не подтверждено; утверждения о запрете тоже не делаем.

Принятый способ интеграции (решение пользователя, 19 октября 2026): официальные
репозитории Bosch подключены как git submodules, как в v1:

| Путь | Репозиторий | Ревизия |
| --- | --- | --- |
| `firmware/third_party/bsec2` | `boschsensortec/Bosch-BSEC2-Library` | `0dac6ea2…`, обёртка 1.10.2610, BSEC 2.6.1.0 |
| `firmware/third_party/bme68x` | `boschsensortec/BME68x_SensorAPI` | `80ea120a…`, v4.4.8 |

Репозиторий Nimbus хранит только ссылку на коммит; файлы Bosch скачиваются из
официального источника при `git submodule update --init`, их копии в дерево Nimbus
не добавляются. Используются `src/inc`, `src/esp32/libalgobsec.a` и
`src/config/bme680/`; Arduino-обёртка `bsec2.cpp` не компилируется.

SHA-256 на закреплённой ревизии:

- `src/esp32/libalgobsec.a`: `571f40cfeb56971bbec8bd432553d88c4ad58f164d7ee41f4870c80fb08448ca`;
- `src/config/bme680/bme680_iaq_33v_3s_4d/bsec_iaq.config`:
  `bc1cdef169aa28b99ffda85ed0a7c9b08ec0d7f6c1fe2edf4cb298a379db242b`.

Sensing обязателен: при отсутствии файлов submodule конфигурация CMake должна
завершаться `FATAL_ERROR` с подсказкой `git submodule update --init`; флага сборки
без sensing и успешной заглушки нет. Проверка добавляется вместе с компонентом
sensing. Условия выпуска готовой прошивки с `libalgobsec.a` проверяются отдельно
перед публикацией бинарников.
